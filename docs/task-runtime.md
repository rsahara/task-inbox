# Portable Git task runtime v2

Version 2.13 adds [portable task interfaces and `execute`](task-execution.md),
one caller entrypoint for checking conditions, supervised execution and explicitly
bounded continuation. Task business logic remains independent of its execution
host and output consumers. Individual `run`/`io wake` commands remain supported.

Version 2.10 unifies every heartbeat, event, and result in [task I/O](task-io.md).
The old heartbeat writer and per-task enable command are removed.

Version 2.9 adds [retained-resource reports](task-runtime-reports.md) and a read-only
`run report` inventory, including local leftovers of retired terminal records.

Version 2.8 removes completed execution metadata during [normal start/finish](task-runtime-cleanup.md).
Task output stays on main; retries use Git history. No archive tag is created.

Version 2.3 adds opt-in [generation timeout recovery](task-runtime-timeouts.md)
for ordinary exact-parent CAS plus trusted clock observations, with explicit
weaker semantics than strict leases and a coordinated writer upgrade.

Optional [fenced leases](task-runtime-leases.md) support disposable scheduled
executors when an installed integration enforces trusted time and every accepted
destination. Ordinary Git and existing manual tasks retain their defaults.

`bin/task-inbox` is an opt-in task coordinator for an independent Git repository.
Git and Python 3.10+ are its only runtime dependencies. The supported process and
locking model is POSIX: Linux, macOS, or WSL. Native Windows is not currently
supported. Git credentials, commit identity, executable workers and scheduling
belong to the caller. There is no GitHub, Codex, Sites, personal account, task
number, database, or hosted queue dependency.

## Independent company use and customization

Keep the company source/data repositories, remotes, credentials and feedback
separate from any personal installation. The coordinator contacts only the remote
explicitly configured in its `--repo` checkout. It does not send telemetry or
feedback. A company's Git server must permit conditional branch updates and the
runtime's branch/tag namespaces. The protected authority branch must allow the
coordinator's normal fast-forward writes; PR-only branch policies need a separate
task-data repository/branch or a policy adjustment by that environment's owner.

Build either a single executable or an editable source distribution:

```sh
python3 bin/build-task-inbox --output /tmp/taskctl.pyz
python3 bin/build-task-inbox --format source --output /tmp/task-runtime-source.tar.gz
```

The zipapp contains only the runtime modules and the existing Git process helper.
The source archive contains those modules, the helper, both CLI/build scripts,
this document, integration tests, and a file checksum manifest. Neither includes
task data, feedback, personal configuration, Git metadata,
credentials, private journals, reports or generated bytecode.

Extract the source archive into a new company tools repository, commit it there,
and customize it normally. It can also be vendored into a company task repository.
There is no automatic upstream synchronization, update service or return channel.
Keep the integration tests with forks: the authority, fencing and retry protocol
must remain interoperable across all deployed writers of one data repository.
Changing paths/CLI presentation is local; changing wire schemas or ownership
rules requires a coordinated migration of that repository's writers.

Version 2.1 supports an explicitly installed transport adapter for environments
whose approved Git/API gateway preserves the same protocol. See the
[adapter contract, capability checks and recovery profiles](task-runtime-adapters.md).
The default remains direct Git. A branch-only mounted-HEAD push is not a substitute
for an exact-candidate, expected-old update. `transport-check` checks reads and
declared capabilities without creating a run; server write semantics and company
permissions require separate conformance/rollout verification.

## Initialize a data repository

Create a bare repository on any supported Git host, clone it, and configure the
normal Git author identity and authentication for that environment. Empty remotes
are supported; `init` is the only operation allowed to create the authority branch.
The examples assume the source distribution and an independent task-data clone.

```sh
python3 bin/task-inbox --repo /path/to/company-tasks --operation-id init-v2 init
python3 bin/task-inbox --repo /path/to/company-tasks --operation-id add-maintenance \
  task add --id maintenance --title 'Repository maintenance' --max-runners 3 \
  --body-file /path/to/instructions.md --recovery-mode manual
python3 bin/task-inbox --repo /path/to/company-tasks task list
```

Global options precede `task` or `run`. `--remote` defaults to `origin`; `--branch`
defaults to `main`. The selected authority ref is persisted at initialization.
The authority cannot be `task-runtime` or any branch below that reserved run-ref
namespace. Initialization and subsequent configuration reads reject overlapping
namespaces; cleanup also refuses run refs that overlap the authority.
A copied feature branch cannot become a second authority just by passing
`--branch feature`. For an entirely separate test data repository, initialize its
chosen branch explicitly. Arbitrary instruction branches coordinated through the
same main authority are not implemented by this option.

All mutations accept a stable `--operation-id`. Supply one at the scheduler or
controller boundary and reuse it for retries. If omitted, a generated ID is
printed to stderr **before** mutation. A repeated ID with another request is an
error. Task IDs and run IDs may be caller-supplied or default to the operation ID;
IDs are immutable lowercase identifiers and cannot be reused after deletion.

## Configurable locations

Plain `init` discovers direct children of `tasks/` by reading each `task.json`'s
immutable `id`. For a readable directory, use `task add --id 9 --title 'Issue inbox'
--path tasks/9-issue-inbox`. No index, stored slug, or repeated task path is needed;
the default output directory is that directory's `data/`. Duplicate IDs fail
closed. Directory names do not determine identity. Keep paths fixed during runs.
Transport adapters must resolve IDs at the expected authority commit rather than
construct task directories from IDs.

Use `init --index registry/tasks.json --task-root work/items` for an indexed
repository. The index is a JSON object with `schema_version: 1` and a `tasks`
map from immutable IDs to repository-relative directories. The default add path
is `<task-root>/<id>`; `task add --path any/location` selects another directory.
`--data-path reports/my-task` optionally selects a separate output directory.
Directories must not overlap each other, the index, or control metadata.

Archive/unarchive only change task state; files never move. Active and archived
tasks may share a root or use arbitrary separate directories. Existing plain
`init` keeps `tasks/<id>` as the default creation path without an extra index.
Configuration is fixed at initialization; task paths are fixed at creation.
Do not hand-edit the index to move an active task. The runtime control directory
`.task-system` and internal file names (`task.json`, `task.md`, `runtime.json`,
`runs/`) remain stable; no configurable file format or layout plugin is required.

The index records locations only. Status, priority and runtime ownership remain
in the task's files, so two independent copies of task state cannot disagree.
Every location/index update uses the same main transaction as task registration.
Runs pin output and artifact paths; untrusted output cannot write the index,
control metadata, another task, or its own definition/runtime files.

## Data layout and task edits

```text
.task-system/config.json
.task-system/operations/<operation-id>.json
tasks/<task-id>/task.json
tasks/<task-id>/task.md
tasks/<task-id>/runtime.json
tasks/<task-id>/data/**
tasks/<task-id>/runs/<run-id>/run.json
tasks/<task-id>/runs/<run-id>/result.json  # recovery / checkpoint delivery / legacy finish only
tasks/<task-id>/runs/<run-id>/artifacts/**
tasks/<task-id>/runs/<run-id>/cleanup.json
```

Schema 9 keeps normal terminal status, summary, artifact manifest, source, finish time and completion evidence in `run.json`. `run show` reads it from the current tree or ordinary history after cleanup. Slots retain only run ID and generation; owner/machine remain on the run. Shared-data conflict detection uses the pinned content hash. See [interface and migration decisions](task-runtime-slim.md).

Metadata uses JSON so the tool needs no YAML package. Each task has a definition
revision. Task status is `open`, `paused`, `completed`, `cancelled`, or `deleted`.
Execution state comes from the run registry, not another `in_progress` field.
`archived_at` controls listing visibility; it never moves a directory. Completing
one run does not complete a recurring task. Closing/deleting a task requires all
its runs to have finished or been recovered. Deletion leaves a tombstone.

```sh
python3 bin/task-inbox --repo /path/to/company-tasks task show --id maintenance
python3 bin/task-inbox --repo /path/to/company-tasks --operation-id pause-maintenance \
  task edit --id maintenance --expected-revision 1 --status paused
python3 bin/task-inbox --repo /path/to/company-tasks --operation-id close-maintenance \
  task edit --id maintenance --expected-revision 2 --status completed --archive
```

Definition edits require the revision read by the editor. Reducing capacity
cannot remove an occupied slot. Pausing stops admission while allowing existing
runs to finish. Execution pins the definition commit and execution policy at
admission; a later edit does not silently change an existing run's instructions,
timeout policy or recovery mode.

## Acquire, prepare, execute, publish and finish

```sh
python3 bin/task-inbox --repo /path/to/company-tasks --operation-id invocation-123 \
  run start --task maintenance --runner worker-123 --machine host-a
python3 bin/task-inbox --repo /path/to/company-tasks \
  run prepare --task maintenance --run-id invocation-123 --path /path/to/worktrees/run-123
python3 bin/task-inbox --repo /path/to/company-tasks \
  run exec --task maintenance --run-id invocation-123 -- /path/to/worker-program
python3 bin/task-inbox --repo /path/to/company-tasks --operation-id result-123 \
  run finish --task maintenance --run-id invocation-123 --outcome succeeded --summary 'Completed'
```

The start example defaults the run ID to the stable operation ID (`invocation-123`); use that returned ID in subsequent commands, or supply `--run-id custom-run` to choose another name.

`start` establishes authority; it does not launch a worker. Replaying the same
operation returns the original run, including its original snapshot. A runner ID
identifies one serialized execution instance, not an entire machine. A runner
cannot acquire another unfinished run of the same task under another request ID.
If `--machine` is omitted, the accepted start records that caller's hostname;
repeating the same operation from another host returns that original machine ID.
An explicitly supplied `--machine` must remain identical on retry.
Optional `--item-key` also prevents two runs of this task from handling the same
logical item. Cross-task external resource exclusion remains the executor's
responsibility.

`prepare` is replayable and preserves unfinished files. Default mode creates a
dedicated worktree/branch. The coordinator uses immutable objects and unique fetch
refs; it never checks out main, resets the primary checkout, changes its staging
index, or shares FETCH_HEAD. Ports, builds, caches and external services must also
be named/scoped per run by the worker.

Before creating or adopting a workspace, `prepare` records an opaque preparation
identity with the existing authority CAS protocol. Its local intent is durable
before the write, so a lost response replays the same identity. Preparing the same
run in another clone marks prior workspace history unobserved, even before a
checkpoint exists. This diagnostic evidence does not change execution ownership
or grant cleanup permission. Workspace paths remain local.

The first admission upgrades authority schemas 2–8 to schema 9 and the
workspace-provenance writer protocol, only after all existing slots are idle.
Deploy runtime 2.11 to every reader and writer together. Finish or reconcile old
heartbeat runs with their original runtime before upgrading; old binaries cannot
prepare or write a schema-9 authority. Historical run records remain readable.

`--mode workspace` uses an executor-provisioned checkout. Use `--repo` pointing to
that checkout, initially clean at the run's pinned definition commit. No primary
checkout or nested integration worktree is needed. Its reservation cannot be
reused while the previous run is unfinished. The tool never deletes an executor
workspace.

After recovery with verified stop/settlement evidence, inspect and preserve the
old workspace's unpublished output before the executor aligns it to the next
run's pinned definition commit. `prepare --mode workspace` then transfers the
reservation if the checkout is clean; the old run's remote checkpoints and
recovery records remain retained. Recovery based only on a stale heartbeat does
not permit reuse of that workspace because the old writer may still be alive.

`exec` is optional: it runs an explicitly supplied executable and supervises its
process group, independently emitting heartbeats while the command runs. It
stops its child group if heartbeat confirmation or authority checking fails.
Raw output stays in local private log files, not Git or CLI JSON. A durable
execution claim on the authority branch is consumed before spawning the worker;
the local execution receipt additionally protects local replay. Another clone
cannot launch the same run, including before its first work checkpoint. A crash
after claiming but before spawning also retains the claim: inspect/recover and
use a new run for another execution attempt. Do not delete receipts to retry a
side effect. Restoring a run's files does not grant another execution attempt.
`exec` returning does not publish artifacts or finish the run.

For an agent/executor that manages its own worker process, call `run check` before
writes and `run heartbeat` periodically. A supervisor is a helper, not a guarantee
that an arbitrarily suspended process or disconnected machine has physically
stopped. External side effects require their own cancellation/idempotency/fencing.

`publish` saves an intermediate result without releasing the slot. `finish`
publishes output, records a result and releases the slot in one authority commit.
The allowed write areas are `tasks/<id>/data/**` and that run's `artifacts/**`.
Task definitions and ownership files are edited through management operations.
The entire source history and pending/untracked files are checked; forbidden
intermediate edits, merges, symlinks and submodules are rejected. Binary bytes,
file modes and deletions are preserved as Git objects.

Publication and normal finish require a prepared/restored local workspace, even
when no output is expected. An accepted operation can be replayed from any clone
using its receipt. An unfinished publication cannot be completed from a clone
that lacks its source: retry from the original workspace, or restore its remote
checkpoint after confirming the old writer stopped and pending operations
settled. The explicit failed/cancelled `--discard-output` path below is the only
way to finish without a workspace or adoptable source; it retains recovery data.

All shared data is conservatively treated as a read dependency. If it changes
since this run's baseline/last publication, recompute in a new run; Git's ability
to merge different lines is not a semantic validation. Independent run artifacts
can publish concurrently when their shared data baseline remains valid. Published
artifacts are verified at the accepted immutable commit; legitimate later updates
to shared data do not invalidate earlier successful publication or cleanup.

For a failed/cancelled run whose output must not be adopted, use:

```sh
python3 bin/task-inbox --repo /path/to/company-tasks --operation-id cancel-123 \
  run finish --task maintenance --run-id invocation-123 --outcome cancelled --discard-output
```

This releases authority and preserves unadopted local/checkpoint data for
inspection. It does not erase work or resolve unknown external operations.

## Git transaction and fencing contract

Admission, task edits, publication, finish and revocation all use the same
transaction: read authority commit M, evaluate every precondition, build child C,
then push with the exact expected-old SHA. A definite race rejection causes a
fresh evaluation against the new authority commit, never a blind rebase of a
previously approved slot registration. There is no separate aggregate runs
branch and no multi-ref atomicity requirement.

Each slot retains a monotonically increasing generation. Every publication checks
the run ID/generation in the **same main snapshot** used as the conditional push
base. Revocation between check and push changes main and rejects the old writer.
Run IDs are never recycled. `max_runners` bounds valid grants, not the number of
old physical processes that may still be paused or partitioned.

Before push, the exact candidate is pinned by a private local Git ref so GC cannot
remove it while its outcome is unknown. The candidate and request fingerprint are
fsync'd into a local journal. Durable operation receipts live on the authority
branch. Lost responses are reconciled against the same receipt/candidate;
another operation is never silently substituted. If main has advanced from the
candidate's base without its receipt or candidate in history, its old conditional
push can no longer succeed: the same request is revalidated against current main.
Prepared publication output remains fixed. Unknown outcomes remain pending.
Retry the same operation ID; preserve the journal when readback cannot establish
the result. The branch
must not be force-rewritten, and operation receipts must not be pruned by normal
clients. This is a cooperative-writer protocol, not an authorization boundary
against a writer able to arbitrarily rewrite repository history.

## Heartbeats, cancellation and recovery

The shared Git runner keeps automatic maintenance in the foreground without
changing repository/global settings. Executors still need an init/reaper for
orphaned descendants; see [process ownership and Git maintenance](task-runtime-processes.md).

[Task I/O](task-io.md) is used by every run for heartbeats, immutable events/results,
and generation-checked acknowledgements on main. Task inboxes accept requests
without a per-task enable step. Detailed progress is never execution authority.

The runtime uses two run refs:

```text
refs/heads/task-io/<task-id>/runs/<run-id>
refs/heads/task-runtime/<task-id>/<run-id>/work
```

The run I/O stream contains `state.json`, events, and results; it is never merged
into main. Heartbeat state stores run identity, generation, sequence, display
timestamp, and optional progress. `work` checkpoints the actual work history before publication.
Heartbeat liveness and useful work progress are different signals.

Defaults are a 60-second heartbeat and a 300-second unchanged-ref threshold.
Git commit dates are not server receipt times. The observer measures an unchanged
remote SHA with its own monotonic clock; the first observation starts a waiting
period. Linux observation caches are tied to kernel boot identity. On systems
without that identity, a restarted observer conservatively waits again; an
explicit stop adapter is preferable for short scheduled invocations there.
Network/read failures never establish death or release a slot.

Call `run reap --task <id>` at the beginning of an existing schedule to inspect
occupied slots. Declare `--observer-profile retained` only if its observation
files and monotonic-clock identity survive between invocations, or `stateless`
for a fresh clone/VM each time. The default `unknown` diagnoses a new observation
without assuming that another invocation will retain it. Missing recovery evidence
or an unestablished observation horizon returns `needs_attention=true` and exit 2;
it does not imply that a live worker is dead. With `--apply`, stale runs may be recovered automatically **only**
when their pinned policy is `git_only`. No extra daemon, polling job, scheduler or
permanent heartbeat process is required for stop-confirmed recovery.

For `manual` tasks, age never authorizes recovery. An operator may supply explicit
stop/settlement confirmations plus a durable evidence reference:

```sh
python3 bin/task-inbox --repo /path/to/company-tasks --operation-id recover-123 \
  run recover --task maintenance --run-id invocation-123 --confirm-stopped \
  --confirm-operations-settled --evidence 'company-executor:verified-stop-and-receipts'
```

For automation, install a trusted environment-specific stop checker and pass its
absolute executable path via `run reap --apply --stop-check /path/to/checker` or
`run recover --stop-check /path/to/checker`. The tool does not execute a stop
checker chosen by repository content. The checker receives the run JSON on stdin
and returns a JSON object containing:

```json
{
  "repository_id": "same repository UUID as input",
  "authority_ref": "refs/heads/main",
  "task_id": "maintenance",
  "run_id": "run-123",
  "generation": 1,
  "writer_stopped": true,
  "children_stopped": true,
  "external_operations_settled": true,
  "pending_git_operations_settled": true,
  "evidence": "durable verified receipt reference"
}
```

The adapter must authenticate to its executor, verify termination of all writers
and children, and reconcile pending Git/API operations using their original
identities. A superficial `cancelled` label is insufficient. No cloud-specific
adapter is bundled; companies implement this contract against their own executor.
Unknown/false fields, mismatched identities, malformed output, failure or timeout
keep ownership and return an actionable blocked/unknown status. Checks can run
before age thresholds, so a verified cancellation need not wait five minutes.
The adapter's evidence is a trusted assertion, not independently proven by Git.

Recovery marks the old run `lost`, records evidence/cleanup retention and releases
only its slot. A replacement uses a new run ID/generation. Recovery does not rerun
an old command, repeat a completed review, delete its checkpoint or assume that a
new machine can delete the old machine's local files. Heartbeat and main are
different refs; false suspicion concurrent with heartbeat renewal is possible,
but a revoked writer cannot publish through this protocol.

## Restore and cleanup

A still-authorized run can be restored into another clone from its remote work
checkpoint after confirming the old writer/children stopped and external/pending
operations settled:

```sh
python3 bin/task-inbox --repo /path/to/new-clone run restore --task maintenance \
  --run-id invocation-123 --path /path/to/restored-worktree --confirm-stopped \
  --confirm-operations-settled
```

The original instruction commit and run identity are retained. The restored
history must contain the published source and remain within the allowed run
boundary. Files never committed/checkpointed before the old environment vanished
cannot be reconstructed. Lost/revoked runs cannot be resurrected by restore.

For newly admitted runs, finish records deletion targets in the same authority
commit as its result and slot release. After confirmation it attempts cleanup;
the next normal start of this task retries leftovers. A subsequent conditional
commit removes disposable execution metadata; cleanup creates no archive tag.
Save required diagnostics as artifacts before
finish; intermediate source history and raw logs are disposable under this policy.

Finish relinquishes the workspace: manually managed workers must stop writing
and settle children/external operations first. Runtime-owned clean worktrees and
matching local branches are removed when invoked from a surviving checkout.
The currently used checkout, executor-owned workspaces, unknown process state
and unpreserved files are retained. Other machines collect their own local files
when they next run the tool. Lost/revoked or discarded-output runs retain their
recovery data.

The explicit command still reports a plan and supports retries:

```sh
python3 bin/task-inbox --repo /path/to/company-tasks run cleanup --task maintenance --run-id invocation-123
python3 bin/task-inbox --repo /path/to/company-tasks --operation-id cleanup-123 \
  run cleanup --task maintenance --run-id invocation-123 --apply
```

Operation receipts and terminal results remain in ordinary main history for idempotency. Matching
confirmed local journals, run records and logs are collected; unknown journals
and their candidate pins remain. A fixed local lock gate protects lock-file
removal. See the [cleanup contract](task-runtime-cleanup.md) for concurrency,
migration and retention details.

Runs admitted by older versions retain their original explicit cleanup procedure:
use `--apply --confirm-stopped` on their owning machine. That legacy path still
records cleanup phases on main, but creates no source tag. Accepted artifacts and
task data remain in the current tree. Older I/O runs without saved records on main retain their
stream for explicit migration; existing tags remain readable and are not purged.

Heartbeat histories create roughly 1,440 commits per active run/day at a 60-second
interval. Timed recovery additionally renews the authority and creates operation
receipts. Cleanup does not change that policy or force host Git garbage collection.

## Existing installations and feedback coverage

Use a separate repository to evaluate v2 first. Cut over an existing installation
only after stopping old admission, settling old publications/external operations,
finishing or recovering all old claims/worker/item locks, and updating every writer
and schedule to one protocol. A copied `schema_version` alone cannot stop an old
binary. Import definitions/artifacts and keep an explicit old-ID/path mapping;
do not copy live tokens, local journals or credentials into the new authority.
The CLI intentionally has no automatic live legacy migration.

Legacy import and service-specific rollout belong to the consuming repository.
This package does not inspect task numbers, legacy lock names or service dispatch.
Existing repositories keep their paths. First admission after the coordinated
runtime upgrade moves an idle authority to schema 9; older writers reject it.
There is no live layout migration command.

## Validation

```sh
python3 -m unittest discover -s test -p 'task_*test.py'
```

Tests use real bare remotes and independent clones, plus linked worktrees and an
executor-style standalone checkout. They exercise concurrent capacity, item
claims, operation replay, candidate reconciliation, revocation during push,
definition pinning, data conflicts, binary artifacts, forbidden history,
heartbeat observation, stop-adapter evidence, cancellation without adoption,
cross-clone restoration, interrupted cleanup and code-only distributions.
Run these checks locally; test Actions are not required. A local Linux pass does
not establish that macOS, another supported Python version, a particular company
host, protected-branch policy or executor adapter has been validated.
